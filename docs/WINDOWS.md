# Windows: проверка и эксплуатация

Дата: 12 октября 2026. Целевая ОС — Windows 11 x64. Текущая машина: RTX 3080 с 10 ГиБ VRAM, около 64 ГиБ RAM; драйвер NVIDIA 591.86. `llama-server --list-devices` обнаруживает CUDA0 / RTX 3080. Используются закреплённые пакеты llama.cpp b11552 / CUDA 12.4, включая библиотеки CUDA; SHA256 и размеры находятся в каталоге приложения.

## Что проверено

| Проверка | Результат и границы |
|---|---|
| Нативный Unicode SendInput | Кириллица, латиница, emoji, Tab, пустые строки, пробелы, символы кода и CRLF в собственном Qt-редакторе переданы буквально |
| Отмена печати | В нативном тесте после первого символа следующие символы не отправляются |
| Глобальные сочетания | Реальная регистрация и WM_HOTKEY через Qt; конфликты и освобождение регистраций дополнительно покрыты контрактными тестами |
| Фокус | Нативный тест переводит фокус во второе собственное окно того же процесса: следующие символы не отправляются; смена PID и цели до запуска worker также покрыта тестами |
| DPI | Нативный захват собственного тестового окна на двух мониторах 100% / 200%; обрезка синтетической области при 100/125/150/200%, включая отрицательные координаты |
| Хранилище ключа | Запись / чтение / удаление синтетического значения в Windows Credential Manager с отдельным временным service ID; рабочий API-ключ не изменяется |
| Секрет локального сервера | Сеансовый ключ записывается после установки защищённого ACL: владелец, администраторы и SYSTEM; удаляется при завершении движка |
| Модели и движок | Возобновление загрузки, проверка SHA256, безопасная распаковка ZIP, атомарная публикация установки и восстановление отсутствующих DLL покрыты тестами |
| Самостоятельный пакет | ZIP с `.exe`, Python и Qt; frozen smoke проверяет GUI, диагностику, синтаксис, loopback OCR, отмену и одноразовый ключ в Credential Manager; отдельный bundled smoke прогревает настоящую модель |
| Интерфейс | Светлая / тёмная темы и состояния ошибок отрендерены; для offscreen на Windows явно загружаются системные шрифты без их распространения в пакете |
| CPU и оборудование | Отдельный CPU-движок без CUDA; настоящий короткий OCR — 2,672 с. GPU обнаруживается через закреплённый движок; оценка памяти проверяется до загрузки, недостаток памяти и отсутствующий драйвер покрыты тестами |
| Первый запуск | Мастер сохраняет явный выбор local / OpenRouter и GPU / CPU; загрузка и облачный запрос запускаются последующей командой пользователя |

В «Распознавание → Дополнительно → Проверить оборудование» показываются ОС, архитектура, RAM и свободная память GPU. Оценка потребления модели предварительная: фактический расход зависит от контекста и области. CPU отключает выгрузку слоёв и vision-проектора на GPU. Ошибка подготовки не включает CPU или облако автоматически. Два режима движка хранятся отдельно, GGUF-файлы общие.

Отдельная нативная проверка `python -m scripts.verify_windows_onboarding` запускает свою упакованную копию в новом диагностическом каталоге, выбирает CPU клавиатурой и проверяет сохранённые настройки. События отправляются только окну с PID запущенной тестовой копии; системный буфер и чужие окна не используются. [Результат](checks/windows-onboarding.json).

Windows WDDM может сообщать через CUDA бюджет процесса, превышающий свободную физическую VRAM. Перед загрузкой используется также NVML из установленного драйвера NVIDIA; доступный объём берётся по меньшей из двух оценок. Из-за различий нумерации одинаковых видеокарт используется меньший свободный объём среди совпадающих моделей. При недоступной общей оценке интерфейс сообщает об этом, а отдельные модели проверки загружаются последовательно. Сведения о Windows и памяти устройства: [официальная документация NVIDIA NVML](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceQueries.html).

RAM показывается также с доступным объёмом. На macOS оценка использует нативный `vm_stat`, его размер страницы и свободные / неактивные / speculative страницы; при неизвестном формате доступный объём остаётся неизвестным. Разбор проверен контрактными тестами, новый нативный запуск Mac не выполнялся.

Если две локальные модели не помещаются одновременно, проверка текста временно выгружает основную модель и восстанавливает её после получения предложений. При отмене повторная загрузка не продолжается; перед новым OCR нажмите «Подготовить». Сбой восстановления не удаляет уже полученные предложения и показывается в статусе.

На текущей машине реальная проверка недостатка GPU-памяти успешно восстановила OCR после отказа Qwen 4B; нехватку памяти после выгрузки тоже нельзя считать успешной проверкой текста. В явно выбранном CPU-режиме LightOnOCR и Qwen 4B одновременно загружены, предложение получено за 12,656 с, исходник сохранён, reviewer выгружен. Это отдельный проход после первичного OCR; он не относится к метрике 4 с. [GPU-отказ и восстановление](checks/windows-review-memory.json), [две модели CPU](checks/windows-review-cpu.json).

Воспроизведение: `python -m scripts.verify_review_lifecycle --data-dir artifacts/windows-data --acceleration cpu`. Для проверки отказа при действительно недостаточной VRAM: `--acceleration gpu --expect-memory-rejection`. На машине, где обе модели по отдельности помещаются, но вместе не помещаются, доступна проверка успешного переключения `--expect-sequential`. Скрипт использует один синтетический эталон и не пишет исходный / предложенный текст; он проверяет жизненный цикл, а не точность на реальных VDI-снимках.

Воспроизведение нативной проверки: `python -m scripts.verify_windows`. Результат записывается в `artifacts/windows-native.json`. Скрипт открывает отдельное тестовое окно, проверяет владение фокусом перед вводом, не использует системный буфер и не захватывает чужие окна. При потере фокуса ввод останавливается.

## Границы приёмки

Проверенный редактор — QPlainTextEdit без автоматического закрытия скобок и кавычек. Notepad, VS Code, IDE и удалённые редакторы не объявляются проверенными по результату этого теста. Shift+Home является настраиваемым профилем; его поведение зависит от редактора. Удалённое перемещение курсора внутри VDI локальная ОС обнаружить не может.

Cisco VDI требует реального сеанса, точного названия клиента и номера сборки. На текущей Windows-машине рабочий ключ OpenRouter сохранён в Credential Manager. После разрешения пользователя выполнен настоящий OCR / reviewer через недорогую `qwen/qwen3-vl-8b-instruct`: один синтетический снимок до системного clipboard за 4,562 с, два запроса $0,000274725. Предварительная отмена и настоящий отказ HTTP 401 сохраняют буфер. Отдельная [отмена после отправки тела запроса](checks/windows-openrouter-cancel.json) завершает ожидание за 0,046 с и сохраняет все форматы буфера; окончательная стоимость отменённой генерации неизвестна. [Отчёт OCR](checks/windows-openrouter.json), [границы и методика](BENCHMARKS.md). Source GUI с нативным захватом, выделением и предпросмотром отдельно проверен: [отчёт](checks/windows-openrouter-gui.json). В этом запуске задержка составила 11,922 с; проверка использует события Qt и отключает hotkeys собственного диагностического экземпляра. EXE из предыдущего ZIP также проверен: нативный hotkey и SendInput мыши запускают выделение → облачный OCR → буфер / видимый предпросмотр, верхняя оценка задержки 9,437 с. [Отчёт EXE](checks/windows-frozen-openrouter.json) содержит проверенный SHA256 бинарника и связь с ZIP. Отдельный диагностический процесс остановлен принудительно, исходный буфер восстановлен; обычная Desktop-копия сохранена. Реальные целевые снимки, медленная сеть и macOS ещё требуют приёмки.

Повторная нативная приёмка macOS после изменений выполняется на Mac; Windows не может подтвердить работу Quartz, разрешений macOS и подписи `.app`. Для этого также добавлена матрица GitHub Actions, но её удалённый запуск не выполнялся в этой сессии. Публичный выпуск требует сертификатов подписи и нотарификации Mac. Текущие пакеты предназначены для пилотного использования.

## Сборка

`python scripts/build_windows.py` создаёт `artifacts/builds/windows/ctrlCctrlV-windows-x64.zip`. Распакуйте ZIP целиком; каталог `_internal` нужен приложению. Сборщик использует системные UCRT / ICU Windows 11 и исключает случайные несовместимые DLL из PATH разработчика. Для отладки доступен `--console`.

При открытом ZIP, который Windows запрещает заменить, создаётся новый архив с уникальным суффиксом и собственным SHA256. Сборщик сообщает точное имя; старый открытый пакет сохраняется. Чтобы перейти на новую сборку, сначала завершите старую копию через её меню «Выход»: повторный запуск с тем же каталогом данных открывает уже работающий экземпляр.

Приложение не требует прав администратора. SendInput может быть заблокирован при попытке писать в процесс с более высоким уровнем прав или защищённый рабочий стол. Это не исправляется скрытым повышением прав; приложение показывает ошибку ввода. Основание: [Microsoft SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput).

## OCR и четыре секунды

Загрузка и прогрев измеряются отдельно. После готового снимка время включает PNG-кодирование, полный ответ и копирование. Превышение 4 секунд не прерывает OCR. Windows-замеры выбранной LightOnOCR публикуются в [BENCHMARKS.md](BENCHMARKS.md); границы качества и скорости сохраняются явно. Результат с offscreen-буфером является изолированным диагностическим замером и не доказывает время записи в системный clipboard.

## Обновлённый интерфейс и пакет

Пакет `artifacts/builds/windows-ui/ctrlCctrlV-windows-x64.zip` содержит переработанный интерфейс. 238 тестов, frozen GUI / loopback OCR / отмена / хранилище и нативный первый запуск проверены в новой сборке; [отчёт](checks/windows-ui.json). Настоящая LightOnOCR 0.8B прогрета из нового EXE в CPU (2,953 с) и GPU (3,750 с), оба процесса завершились с кодом 0; [отчёт с SHA256](checks/windows-ui-frozen-models.json). Это время диагностического запуска / прогрева, а не задержка OCR до буфера. Платные облачные запросы после изменения UI не повторялись.

CI использует `macos-15` ARM64 и проверяет архитектуру до сборки. GitHub [отключает macOS 14 runner 2 ноября 2026](https://github.blog/changelog/2026-10-01-github-actions-macos-14-runner-image-retirement/); нативная приёмка заявленной минимальной macOS 14 остаётся отдельной задачей. Удалённый workflow в этой сессии не запускался.
