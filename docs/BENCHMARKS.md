# Замеры OCR на macOS и Windows

## Новый benchmark буквальной точности: 12 октября 2026

`scripts/benchmark_acceptance.py` измеряет OCR на изображениях с буквальными эталонами. Без `--execute` команда только проверяет локальный manifest и формирует план: провайдер не создаётся, сеть и ключи не используются, модель не загружается. Это относится к обоим значениям `--provider`, включая `openrouter`. Облачный бюджет по умолчанию **0 USD**. Буфер, история, ввод текста и ручная тяжёлая проверка в этот benchmark не входят.

### Точная схема manifest

Корень — JSON-массив из 1–1000 объектов. Обязательны все шесть первых полей; другие поля, кроме двух перечисленных необязательных, запрещены:

| Поле | Формат |
|---|---|
| `id` | Уникальная строка из 1–64 ASCII-символов; первый — буква или цифра, остальные — буквы, цифры, `_`, `.`, `-` |
| `image` | Относительный путь к декодируемому изображению, с `/` как разделителем |
| `text` | Относительный путь к буквальному эталону UTF-8, с `/` как разделителем |
| `kind` | `text`, `code` или `table` |
| `language` | Языковой тег: 2–8 латинских букв, затем необязательные части из 1–8 букв/цифр через `-`; например `ru`, `en`, `ru-en` |
| `font_size` | Метка `small`, `medium`, `large` или `mixed` |
| `source` | Необязательно: `real` или `synthetic`; по умолчанию `synthetic` |
| `challenging` | Необязательно: JSON boolean; по умолчанию `false` |

```json
[
  {
    "id": "synthetic-demo-01",
    "image": "sample.png",
    "text": "sample.txt",
    "kind": "code",
    "language": "ru",
    "font_size": "medium",
    "source": "synthetic",
    "challenging": false
  }
]
```

Пути разрешаются внутри каталога manifest; абсолютные пути, `..`, обратная косая черта, `:`, UNC/alternate streams и ссылки наружу запрещены. Изображение и эталон должны существовать. Лимиты: manifest 1 000 000 байт; изображение 32 000 000 байт и 40 000 000 пикселей; эталон 1 000 000 байт и 10 000 Unicode-символов. Вычисление редактирования отдельно ограничено 10 000 000 ячеек; превышение регистрируется как ошибка, а не заменяется приближённой метрикой. Для `table` эталон — прямоугольный strict CSV, включая первую строку как данные. Значения с запятыми, кавычками и внутренними переносами записываются правилами CSV; преобразования чисел и формул нет.

Реальные эталоны следует хранить в отдельном локальном каталоге вне публикуемых артефактов. Для требуемого реального набора нужны минимум 6 обычных текстов, 10 фрагментов кода, 8 таблиц и 6 отдельных сложных случаев. В этих счётчиках `challenging=true` исключается из обычных трёх групп; все примеры должны явно иметь `source=real`. Поле `real_corpus_complete` проверяет только такую **композицию manifest**, а не происхождение изображений, качество OCR или факт приёмки; исполнение отражает отдельное поле `executed`. Синтетика не удовлетворяет этому внешнему критерию. Dry-run не содержит утверждения о пройденной приёмке.

### CLI и проверенный dry-run

Из корня репозитория:

```powershell
# Один явно синтетический демонстрационный пример, без OCR и сети.
.venv/Scripts/python.exe scripts/benchmark_acceptance.py --manifest artifacts/ui-polish/benchmark-example/manifest.json --provider local --model lightonocr-3-0.8b --output artifacts/ui-polish/benchmark-example/dry-run-local.json

# Даже неизвестная модель облака здесь не вызывает обращения к каталогу API.
.venv/Scripts/python.exe scripts/benchmark_acceptance.py --manifest artifacts/ui-polish/benchmark-example/manifest.json --provider openrouter --model org/vision-model --output artifacts/ui-polish/benchmark-example/dry-run-cloud.json

# Воспроизводимый отдельный корпус из 30 синтетических примеров.
.venv/Scripts/python.exe scripts/generate_acceptance_fixtures.py --output artifacts/ui-polish/benchmark-synthetic
.venv/Scripts/python.exe scripts/benchmark_acceptance.py --manifest artifacts/ui-polish/benchmark-synthetic/manifest.json --provider local --model lightonocr-3-0.8b --output artifacts/ui-polish/benchmark-synthetic/dry-run.json

# Явный локальный запуск на уже установленной модели и движке.
.venv/Scripts/python.exe scripts/benchmark_acceptance.py --manifest artifacts/ui-polish/benchmark-synthetic/manifest.json --provider local --model lightonocr-3-0.8b --output artifacts/ui-polish/benchmark-synthetic/local-lighton-08b-app.json --execute --repeats 1 --max-output-tokens 4096 --acceleration gpu --capture-format auto --data-dir artifacts/ui-polish/benchmark-table-diagnosis/runtime-repro
```

Оба демонстрационных dry-run фактически завершились с exit 0: `executed=0`, `planned_requests=1`, `budget_usd=0`, `reserved_usd=0`, `real_examples=0`, `synthetic_examples=1`, `rows=[]`. Dry-run большого синтетического корпуса также завершился с exit 0: запланировано 30 запросов, выполнено 0; реальных примеров 0, синтетических 30. Это подтверждение команды/валидатора, без замера OCR.

Обязательны `--manifest`, `--provider local|openrouter`, `--model`, `--output`. Дополнительно: `--budget-usd` (неотрицательное десятичное число, default 0), `--execute`, `--repeats` (1–20, default 1), `--max-output-tokens` (1–131072, default 4096), `--data-dir`, `--acceleration gpu|cpu` (default gpu), `--capture-format auto|text|csv` (default auto). `--data-dir` указывает уже подготовленный локальный кэш; без него используется стандартный каталог приложения. В выполненном повторе каталог `runtime-repro` был отдельно подготовлен с локальными junction-ссылками на установленную модель/движок; сама CLI-команда его не создаёт. Новый benchmark не устанавливает и не скачивает модели. Локальный процесс использует собственный loopback-порт и уникальное имя временного session-key, сохраняя обычные OCR/review key-файлы приложения.

Генератор использует существующие `ctrlcctrlv.fonts.prepare_fonts()` / `monospace_font()`, фиксирует фактически разрешённую семью шрифта, пиксельный размер, DPI и геометрию в отдельном `generation.json`. При отсутствии пригодного моноширинного шрифта генерация останавливается. Никаких дополнительных зависимостей шрифтов или загрузок нет. `--font-family` выбирает установленный шрифт; повторная генерация существующих файлов требует явного `--overwrite`. Табличные PNG показывают значения в сетке, а эталон содержит буквальный CSV. Табуляция рисуется как четыре моноширинных пробела, но эталон хранит настоящие табы: это ограничение восстановления по пикселям, а не разрешение на нормализацию. Пиксели могут отличаться между ОС из-за шрифтов/fallback emoji; для сравнения платформ нужно копировать одни и те же изображения.

По последнему указанию пользователя реальные примеры отсутствуют и заменены **отдельным синтетическим измерением**, а Mac и VDI сейчас не тестируются. Чистая Windows VM не проверена. Ни один из этих пунктов не считается пройденным благодаря генератору или тестам Qt.

### Исправленный замер результата приложения: 12 октября 2026

Основные метрики теперь проходят производственный путь `recognition_prompt(capture_format)` → `recognize_result()` → `table_result()`. Это исправление методики benchmark: код OCR/форматтера приложения не менялся. При `auto`/`csv` распознанная целая HTML/Markdown-таблица преобразуется штатным форматтером в CSV; `text` сохраняет текстовый результат. Отдельные числовые `raw_metrics` сравнивают исходный `raw_text`, когда он доступен, а `raw_available` отмечает доступность. Содержимое ответа не сохраняется. Старые адаптеры с `recognize(png, operation)` поддерживаются без пробного запроса и без повторов после TypeError.

Выполнен **один повтор 30 синтетических примеров** на той же установленной LightOnOCR-3 0.8B / RTX 3080, в отдельном процессе/порту, с локальными ссылками на существующий кэш и session-key только в каталоге артефактов. Запросов областей 30, штатный warm-up runtime 1; ошибок/отмен 0. Настройки, UI-state и обычные runtime key-файлы сохранились. Cloud, clipboard/history, загрузок моделей и записи в default profile не было.

### Облачный предел и стоимость

Платный запуск CLI допустим только с явным `--execute`, положительным `--budget-usd` в рамках бюджета пользователя и отдельно предоставленной переменной `OPENROUTER_API_KEY`. Сохранённые ключи приложения этот CLI не извлекает. Отдельный разрешённый artifact-runner выше читает `Credentials().read()` в память и дополнительно проверяет `/key`; это отдельный путь, не изменение CLI. При нулевом бюджете исполнение отвергается до сети и поиска ключа. При положительном бюджете сначала запрашивается текущий публичный каталог OpenRouter: должны быть известны vision-поддержка, context length и цены `prompt`, `completion`. Отсутствующие optional `image`/`request` принимаются как нулевые только вместе с принудительными routing price caps; явно неизвестное значение запрещает запрос. Известная скидка `input_cache_read` не уменьшает резервацию и не может быть выше обычной входной цены; неизвестное ненулевое дополнительное начисление, в том числе cache write, запрещает запрос.

Перед каждым запросом целиком резервируется верхняя стоимость: **весь context length × цена входного токена** (включая токены изображения и инструкции) + **max output tokens × цена выходного токена** + цена одного изображения + цена запроса. Это намеренно консервативная оценка по внешнему контракту модели; она может запретить практически более дешёвый запуск. Расчёт остатка использует `Decimal`. Routing получает округлённые вниз `provider.max_price` для всех четырёх цен и `allow_fallbacks=false`; транспорт не повторяет запрос автоматически. Неизвестной оценки или недостаточного остатка достаточно для отказа до отправки.

Ошибка/отмена сохраняет всю резервацию; она не освобождается для следующего запроса. Ошибка прекращает повторы этого примера, отмена — весь запуск. Явные `--repeats` повторяют только успешно завершённые примеры; платных повторов после ошибки нет. Фактический `usage.cost` выводится отдельно от резервации и остаётся `null`, если стоимость не получена; отмена не означает бесплатный запрос. Если наблюдаемая стоимость превышает оценку, `budget_overruns` увеличивается и следующие запросы не отправляются. Само внешнее начисление нельзя отменить этим клиентским контролем.

### Метрики, cold/warm и числовой отчёт

Метрики не заменяют друг друга:

- `exact`: буквальное совпадение всей строки.
- `exact_ignoring_one_final_newline`: после удаления не более одного финального CRLF/LF/CR с каждой стороны; остальные пробелы/переносы остаются.
- `character_errors` / `character_accuracy`: расстояние Левенштейна по Unicode codepoints и `max(0, 1 − errors / max(reference_length, 1))`.
- `indentation_exact` / `blank_lines_exact`: последовательность начальных пробелов/табов по строкам и позиции/содержимое пустых строк; нечувствительное к пробелам сравнение не применяется.
- Для таблиц `csv_valid`, `csv_cells_exact`, `csv_cell_accuracy`, `csv_cells_compared`: одинаковые значения на одинаковых координатах; лишние/пропущенные ячейки включены в знаменатель. Первая строка также сравнивается.
- Успех, ошибка, отмена и отказ бюджета хранятся отдельно; ошибки не отбрасываются ради красивой статистики.

`elapsed_seconds` заканчивается до посимвольного выравнивания и включает чтение/подготовку PNG, OCR и штатное форматирование результата. Локальный `startup_seconds` включает preflight, запуск, загрузку и штатный image warm-up. `cold_scope=1`: первый успешный **первоначальный** локальный запрос вместе с startup; `cold_scope=2`: первый облачный запрос клиента, без знания cold-состояния удалённой модели. Только первая попытка относится к cold; если она ошибочна, успешной cold-выборки нет. Остальные успешные запросы относятся к warm. p50/p95 вычисляются линейной интерполяцией по успешным попыткам, с явными `cold_samples` / `warm_samples`; времена неуспешных попыток остаются в строках отчёта. Одного cold-наблюдения недостаточно для надёжного p95. Ни один показатель не измеряет полный захват → системный буфер/VDI и не доказывает цель 4 секунды.

Новый отчёт JSON версии `schema_version=2` с `app_level_metrics=1` и `capture_format_id` (0=auto, 1=text, 2=csv) содержит ID модели/примеров и числовые показатели, `null` для неизвестных величин, состав набора, план числа запросов, счётчики состояний, резервацию и измеренную стоимость, startup/cold/warm статистику и `rows`. При наличии исходного ответа каждая успешная строка содержит `raw_available=1` и отдельные числовые `raw_metrics`; при ограничении расчёта только raw-диагностики появляется `raw_metric_refused=1`. В dry-run `rows=[]`: область будущего замера не означает его исполнения. Исторический отчёт версии 1 сохранён отдельно с прямой OCR-методикой. Текст эталона/OCR, картинки, пути пользователя, provider body, сообщения исключений и ключи в отчёт не попадают. Эталоны UTF-8 читаются без замены CRLF/LF. JSON записывается атомарно; путь отчёта не может совпасть с manifest, изображением или эталоном. Exit codes: 0 — dry-run/успешное исполнение; 2 — отказ в проверке или подготовке; 3 — записанный отчёт с ошибкой, отменой, отказом бюджета или превышением оценки.

Полный pytest/сборку выполняет интегрирующий этап. Реальный 30-корпус, реальные модельные рекомендации и платформенная приёмка остаются отдельными проверками.

Ответ ограничен 512 токенами; повторов и перехода на другую модель нет. Каталог на момент проверки показывал $0,25 / $0,75 за миллион токенов. Стоимость по `usage.cost`: $0,000125235 и $0,000149490, всего **$0,000274725**.

Первичный OCR от готового изображения, включая PNG, полный ответ и запись в **системный Windows clipboard**, занял **4,562 с**. Цель 4 с превышена; полный ответ принят и скопирован. Получено 130 символов: отличие от эталона только в отсутствии завершающего перевода строки. Отдельная проверка заняла 4,765 с и оставила предложение без изменений. Исходник сохранён, автоматической публикации предложения нет, выбор пустого набора исправлений сохраняет исходник.

Предварительная отмена не отправляет запрос и сохраняет буфер. Настоящий запрос с заведомо неверной авторизацией получает HTTP 401 и также сохраняет буфер; пользовательский ключ в нём не используется. Исходные MIME-форматы системного буфера восстановлены после проверки; восстановление пропускается, если Windows сообщает, что пользователь сменил буфер.

Дополнительный отдельный запрос проверяет отмену **после отправки тела HTTPS POST**. Диагностический транспорт использует [событие httpcore `send_request_body.complete`](https://www.encode.io/httpcore/extensions/), игнорирует данные события и через 150 мс запрашивает отмену. Производственный `OCRProvider` завершает ожидание с `Cancelled` через **0,046 с**, закрывает транспорт и не принимает полный ответ; все форматы системного буфера и его Windows sequence number сохранены. На момент отмены заголовки ответа ещё не получены. Это подтверждает прекращение клиентского ожидания после передачи тела, но не остановку вычислений удалённого провайдера.

[Отчёт отмены](checks/windows-openrouter-cancel.json) содержит шесть успешных проверок. Три наблюдения совокупного счётчика расходов ключа в течение четырёх секунд не показали увеличения. Окончательная стоимость отменённой генерации неизвестна: её ID / usage не получены, сервер может учесть расход позднее. Воспроизведение на Windows: `python -m scripts.verify_openrouter_cancel`; скрипт отправляет один потенциально оплачиваемый запрос и не пишет в буфер.

Перед запросом пиксели выбранного изображения сравниваются с эталоном: при отличии загрузка в облако не начинается. Изображение в предпросмотре сохранено полностью, публикация происходит в GUI-потоке. Ручная правка не меняет буфер до кнопки «Копировать текст». ## Подготовка различий для предпросмотра

На синтетическом тексте из 4000 одинаковых строк и одной исправленной строки полный `SequenceMatcher(autojunk=False)` занимал 1,161 с. Тест удерживает подготовку в рабочем потоке, редактирует текст в UI и проверяет отмену / отбрасывание устаревшего предложения. Отдельный тест проверяет, что matcher получает только изменённую середину и повторное чтение не пересчитывает её. Это устраняет выявленную задержку на повторяющихся границах, но не доказывает постоянное время для любых структур текста.

Повторный запуск шести длинных областей **перезапускает и прогревает Qwen перед каждой областью**, исключая ожидание отменённого предыдущего запроса. Ни одна из шести не завершилась до 4 секунд. [Изолированные длинные области](benchmarks/vision-patches-qwen4-isolated-long-m4pro.json). Во всех случаях подготовка моделей исключена, OCR Vision, чтение PNG, полный ответ и проверка исправлений включены; системный буфер не используется. При таймауте частичный ответ не применяется. Следовательно, компактные исправления в проверенной конфигурации не решили требование скорости и не включены в рабочий OCR.

## Кроссплатформенный кандидат: RapidOCR / PP-OCRv5

После отказа от Vision проверен RapidOCR 3.10.0 с ONNX Runtime 1.31.0, CPU, 4 intra-op потока и 1 inter-op поток. Детектор — PP-OCRv5 mobile, распознаватель — eslav либо cyrillic PP-OCRv5 mobile. Модели ONNX — конвертации RapidAI; filenames, размеры и SHA256 записаны в отчётах и проверены по закреплённому списку. Для каждой конфигурации в `model_files_used` указаны только загруженные в OCR модели; `models` перечисляет все файлы экспериментального кэша. Детектор и один распознаватель занимают суммарно примерно 12,7–12,9 МБ файлов; это не потребление RAM.

Обе языковые модели по документации PaddleOCR поддерживают русский и английский. ONNX Runtime позволяет использовать общий движок на целевых платформах; в этой работе измерен **только Mac**, совместимость приложения и скорость Windows ещё не проверены. [Модели PaddleOCR](https://paddlepaddle.github.io/PaddleOCR/latest/en/version3.x/algorithm/PP-OCRv5/PP-OCRv5_multi_languages.html), [список RapidOCR](https://rapidai.github.io/RapidOCRDocs/latest/model_list/).

Скачивание, проверка файлов и первый вызов вынесены в подготовку; GPU / CoreML не используются. После подготовки HTTP-вызовы запрещены внутри процесса; попытка сети прервала бы эксперимент. Настройки классификации ориентации выключены для горизонтальных редакторских снимков.

`scripts/ocr_layout.py` оценивает ширину символа и межстрочный шаг по распознанным рамкам, соединяет фрагменты одной строки, восстанавливает пробелы и пустые строки; убирает только одинаковые геометрически перекрывающиеся символы. Размер шрифта, координаты строк из генератора и эталонный текст не участвуют в восстановлении. Этот способ не доказывает точное число пробелов для любых шрифтов, особенно пропорциональных, или начальные отступы при отсутствии строк с нулевым отступом. Координатные случаи и пересечение одинаковых / разных символов покрыты тестами.

Скорость подходит для дальнейшей проверки, но буквальная точность пока недостаточна: например, обе модели распознают латинское `name` как кириллическое `пате` внутри смешанной строки. Никакие замены букв по словарю или эвристики исправления кода автоматически не применяются. В приложение кандидат пока не интегрирован; модель по умолчанию остаётся прежней.

Отчёты содержат только синтетические строки и рамки: [eslav](benchmarks/rapidocr-v5-eslav-cpu-m4pro.json), [cyrillic](benchmarks/rapidocr-v5-cyrillic-cpu-m4pro.json). Воспроизведение: отдельное окружение с `rapidocr==3.10.0 onnxruntime==1.31.0`, затем `python -m scripts.benchmark_rapidocr --language cyrillic`. Модели скачиваются из закреплённой версии RapidAI `v3.10.0` в экспериментальный кэш. Окружение и модели приложения не изменяются.

## Явная локальная проверка LightOn → Qwen: 13 октября 2026

Первичный LightOnOCR-3 0.8B работает на GPU, затем выгружается; отдельная Qwen3-VL 4B Q4_K_M проверяет тот же PNG и точный результат приложения на **CPU**. Для GPU Qwen штатная проверка памяти отказала: доступно около 4,0 ГБ при оценке 4,9 ГБ. CPU выбран явно; проверка памяти не обходилась, автоматического переключения режима не было. Использован проверенный llama.cpp b11552, отдельный временный профиль с копиями только моделей и движков, собственные процессы и ключи. Настройки, история и clipboard пользователя не использовались.

Позиционное выравнивание считает **76 исправленных и 21 новую ошибочную позицию**; 117 прежних ошибочных позиций остались. Среди новых позиций нет дополнительных вставленных символов, но есть повреждённые ранее правильные символы. Для CSV отдельно зафиксированы **14 новых ошибочных ячеек и 0 исправленных**. Ухудшившиеся по символьной дистанции числовые IDs: 19, 20, 21, 24; новые ошибки ячеек — IDs 20 и 30. ID соответствует позиции 1–30 в manifest, не имени или содержимому примера.

**Ограничение качества:** суммарное улучшение не означает безопасного автоматического исправления. На этом наборе Qwen ухудшает отдельные результаты и буквальные значения таблиц. Этот замер не подтверждает отсутствие новых ошибок, автоматическое улучшение любого результата или качество на реальных пользовательских снимках. Пользователь должен оценивать предложение в сравнении и выбирать правки явно; итоговый выбор/копирование здесь не выполнялись. Это измерение запросов готовых PNG, без системного захвата, отображения Comparison и clipboard, поэтому оно также не подтверждает скорость полного пользовательского сценария.

Метрики сохраняют Unicode-символы, пробелы, отступы, пустые строки и CR/LF буквально. CSV сравнивается по координатам и строковым значениям без преобразования чисел. Новые/исправленные ошибки рассчитаны `scripts.accuracy.compare_errors`: детерминированное выравнивание Левенштейна, не семантическая экспертиза; повторяющийся текст может давать неоднозначную привязку позиций. Ответы, raw первичного OCR, эталоны и ключи оставались в памяти; отчёт содержит только числовые значения и IDs. Реальных примеров — 0. Прогоны Mac, VDI и чистой Windows VM этим измерением не заменяются.

Первый запуск остановился при подготовке LightOn до обработки каких-либо образцов и сохранён отдельно (fatal stage 1/type 9). Причина не воспроизвелась: отдельный диагностический запуск прошёл проверку оборудования, загрузку и прогрев, затем выгрузил собственный процесс. Координатор разрешил возобновить нулевой запуск; повторов corpus-запросов не было. Успешный основной прогон включает два отдельных blank-image прогрева; диагностика добавила ещё один локальный прогрев. Возможный прогрев первого неудачного запуска не измерен. После основного прогона обе модели выгружены, собственные session-key файлы удалены.
